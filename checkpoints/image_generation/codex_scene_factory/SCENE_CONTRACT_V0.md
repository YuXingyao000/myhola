# 场景制作协议 v0：固定姿态零件与平面支撑

> 状态更新（2026-10-12）：用户明确制作产物应为可跨 CAD 复用的布景模板。当前入口改为 [布景模板生成协议](TEMPLATE_CONTRACT_V0.md)，作者接收占用包络而非单个 STEP；本文件保留此前单件输入、相机和工具讨论，不再代表当前制作任务默认。批量拍摄仍使用其中适用的固定程序检查原则。

## Task

把一个固定姿态 CAD 放入 GPT 制作的可复用环境，以极小的调用循环摸索场景质量。协议固定支撑、坐标、目标与相机边界，保留场景内容的创作自由。

状态：2026-10-12 需求草案，未实现或渲染。用户已确定“目标程序材质、给定姿态、必须接触平面、允许力学不稳定”；具体字段与数值是本轮设计建议，不是已运行结果。本文件是 [整体方案](PLAN.md) 的最小启动子集。

## Assumptions

- 单个不透明目标零件，源几何、旋转、尺度及平面内锚点由请求固定。物理尺寸未知时，记录显式尺寸假设，不由 GPT 根据场景猜测或修改。
- 目标呈现刚制作完成的外观，仅用常量／程序函数驱动 PBR，不用图片贴图；该约束不禁止背景使用已登记的贴图。
- 无刚体模拟、重心判定或沉降；点／边接触允许，`stability_status=not_evaluated`。
- v0 建议内部统一右手坐标系、米、Z 向上；在 `preserve_relative_view` 模式下，通过给 CAD 和相机施加同一平移，使支撑平面位于 `z=0` 且保持输入投影。桌面模式中桌腿和室内地面位于其下方；地面模式中地面顶面位于此处。原点是接口约定，不是所有场景的实际地面海拔。绝对世界坐标被锁定时不能擅自使用这一变换，见下文。
- 首版选择一个足够大的水平、无孔平坦放置区，可属于桌面、地面或其他对象；场景本身和支撑网格不限于 Plane primitive。斜面、曲面和软体支撑暂不在 v0 内。
- `Needs confirmation`：首批场景用途和资产清单、正式尺寸与相机范围、接触容差及制作预算。下面示例只说明接口，不授权批量运行。

## Inputs

### 用户输入与框架配置

用户侧可以保持为 `STEP + camera + scene_prompt`，精确语义由版本化配置补齐，不能把所有必需参数都埋进自然语言：

| 输入 | 最小语义 |
|---|---|
| `cad` | STEP 路径／哈希、实体选择、姿态。仅一个实体时按原始方向作为显式默认；装配或多实体需要明确选择策略，不能擅自选最大实体。文件声明单位与额外物理尺寸假设分别记录 |
| `camera` | 相机位置所属坐标系、距离单位、朝向约定、水平或垂直 FOV、图像宽高；首版透视投影、方形像素、零镜头偏移／畸变可由固定配置提供 |
| `scene_prompt` | 场景用途及外观要求，可以不完整；保留原文，不覆盖精确的几何／相机合同 |
| 框架配置 | 放置／相机耦合策略、程序材质、资产白名单、seed、预览与修复预算、检查阈值、输出格式 |

Pitch／Yaw／Roll 的名称不足以确定旋转；配置必须明确角度单位、对应轴、旋转顺序、内禀／外禀及相机局部朝向轴。输入通过已命名且可验证的 convention 转为 `camera_to_world`／`world_to_camera` 与内参矩阵，渲染器负责转为 Blender 约定，GPT 不解释或重算欧拉角。FOV 和宽高用于确定另一方向视场，不能只传未命名的 `fov=45`。同时提供多种朝向表示且不一致时报告冲突。

### 调用模型前完成的工作

固定预处理器读取 STEP、检查所选实体和单位、按记录的三角化参数输出网格；保留源 STEP、网格摘要、三角形到 B-Rep 面的对应、正确法线／硬边、坐标变换与版本。不以平滑、补洞或倒角修饰改变标签。输入单位声明不等于归一化数据的真实尺寸，后者仍需显式假设。

初版可用 OBJ 作为可检查的交换文件，并用旁路数组／JSON 保存面对应和元数据；STL／OBJ 不能单独承担完整数据合同。Blender 导入后的轴变换、缩放、重排、法线与面对应必须核对，不能假定索引原样保留；也可由固定 loader 直接用顶点／三角形数组构建网格。

预处理产物为 `prepared_target/`：网格与面对应、完整变换／单位、规范相机、包围盒、目标单独渲染的灰模及 mask、拍摄预检报告。这些是可缓存的固定事实，不要求 Codex 每次重复执行。缓存键包含源几何、实体选择、三角化／法线版本；相机与视图参考另按规范相机和目标变换缓存。

在调用模型前检查目标相对于相机是否位于有效深度、是否完整入画、画面占比及目标自身裁切。包围盒可做保守快速检查，边界情况用实际几何投影／参考渲染确认，不能仅看图像中已经被裁剪后的 mask 判断“完整”。再加入标准支撑面检查是否与固定相机冲突；例如相机位于不透明平面下方而目标在上方。严格模式预检不通过即返回输入问题，不调用模型解决不可能的布景。自动调整相机只能作为明确开启的输入准备选项，并输出新相机配置。

### 交给场景作者的请求

一份 `request.json`，由固定程序根据上述产物解析后交给作者：

| 字段 | 语义与责任 |
|---|---|
| `protocol_version`, `request_id`, `seed` | 请求身份与场景随机数流；实际采样结果也要保存 |
| `scene_brief` | 环境用途、支撑类型、背景与照明意图，例如“车间工作台＋侧窗” |
| `target_contract` | 固定旋转／尺度／XY 锚点；落地后的目标包围盒、程序材质配置 ID。GPT 不需要读写源 CAD |
| `support_requirement` | 请求所需的矩形空闲区域、接触容差；尺寸含目标投影包围盒及明确边距 |
| `reserved_volume` | 围绕已放置目标的清空体积；支撑顶面接触例外，不允许其他物体侵入 |
| `camera_contract` | 固定相机内外参、裁切、分辨率与成像配置；作者可据此布景但不能修改 |
| `reference_images`, `preflight_report` | 实际目标灰模／mask、相机预检结论；包围盒不能代替模型对外形的全部视觉信息 |
| `asset_allowlist`, `budgets` | 允许使用的资产及摘要、制作／预览／修复上限；资产可为空，用程序构建即可 |

旋转矩阵、相机矩阵等沿用固定渲染器的显式坐标合同；下方局部示例不代替完整请求。每次只交付一个场景候选，暂不要求 GPT 自动规划整个场景库。

### 不完整提示词的补全边界

采用“精确配置＋可补全描述”组合：已知几何／相机／材质策略先冻结，GPT 可补全缺少的桌面样式、墙面、道具、背景布局和照明方案。结果保存为 `resolved_scene_spec.json`，按字段标注 `user`、`default`、`model` 或 `geometry_derived`，附原始提示和模型／模板版本。

补全过程不得猜 STEP 单位、目标实体、相机坐标与欧拉约定，也不得改源几何或固定视角。自然语言与硬配置冲突时返回可读的冲突项，不静默选择一个版本。语法／类型检查可确定执行合同，但不宣称自动证明全部自然语言意图已经满足。补全与环境编写可在同一 Codex 任务中完成，不要求另设一个规划 agent；执行工具先检查解析后的规格，再运行构建。

## Outputs

作者交付两项逻辑产物；引用外部文件时附依赖目录：

1. `build_scene.py`：只构建环境几何、背景材质、灯光及 World；以明确 seed 和参数构建，不导入目标，不改变相机、颜色管理和渲染内核。
2. `scene.json`：声明场景版本、实际支撑对象及表面区域、清空体积、灯光方案、资产摘要和已经解析的参数。制作早期可以只提供一个实例参数组，后续再扩展变化范围。

`scene.json` 的支撑部分示意（米；坐标均在上述世界系中）：

```json
{
  "protocol_version": "scene-v0",
  "scene_id": "workbench_001",
  "support": {
    "object_id": "workbench_top",
    "surface_region_id": "placement_patch",
    "plane_z_m": 0.0,
    "normal_world": [0.0, 0.0, 1.0],
    "clear_rect_xy_m": [-0.30, -0.25, 0.30, 0.25]
  },
  "reserved_volume_world_m": {
    "min": [-0.12, -0.10, 0.0],
    "max": [0.12, 0.10, 0.30]
  },
  "stability_status": "not_evaluated"
}
```

矩形顺序为 `[xmin, ymin, xmax, ymax]`。区域必须关联求值后的实际网格表面，不能仅凭对象名字或作者自报成立。数字是独立示意，不表示所有 CAD 都适用这个尺寸；真实请求必须匹配其固定尺度与包围盒。

固定程序另输出 `preview.png`、`report.json`、`resolved_scene_spec.json` 和解析后的运行配置；通过检查也仍需真实感审阅。冻结时保留源代码、JSON、允许资产、环境版本、调用摘要与预览，不只保存一张 RGB。

## Processing Protocol

1. **固定目标合同**：先规范源 CAD 与输入相机，再按请求中的坐标策略建立支撑。推荐的 `preserve_relative_view` 模式下，设顶点为 `p_i`，取 `delta_z = -min_i(p_i.z)`，对目标和相机共同追加相同平移，保持二者相对投影并使最低点落在 `z=0`。若输入锁定绝对世界坐标，则保持目标与相机不动，把支撑面设置在原最低点高度，记录实际 `plane_z_m`；若同时强制该平面为零且不满足，报告冲突。共同平移只是显式坐标变换，不是重新构图；所有变换保存，完成后目标／相机均冻结。不能仅移动 CAD 再声称保留输入视角。
2. **制作请求**：用落地后的包围盒生成支撑空闲区域和目标清空体积。向 GPT 提供场景 brief、上述合同、允许资产与输出格式；可使用包围盒代理物体做布景，代理不进入生产输出。
3. **规格补全与环境构建**：GPT 补全允许的场景字段，生成代码和元数据。背景几何复杂度、桌／地样式、墙、道具、表面材质和灯光布置由其设计，始终遵守支撑和相机合同。可见窗口、实际灯光与环境反射应协调。
4. **统一装配与检查**：沿整体方案的隔离构建边界把环境导出为受检查的数据，再由固定内核创建场景并插入 CAD 与相机。最小循环只处理一个任务，但不让环境脚本接管最终目标／相机／标签。
5. **预览与有限修复**：固定渲染程序输出目标视角 RGB、对应灰模／mask 及场景全景，报告坐标、接触、穿插、可见性和资产错误。反馈一次任务的明确问题，使用已配置的修复上限；不变更目标姿态或选最好看的新相机规避失败。
6. **冻结复用**：首个环境实例通过后，使用冻结程序／资产复现。后续再增加参数范围和更多 CAD；未验证的尺寸、姿态和相机范围不能由单个预览外推为已支持。

支撑空闲矩形是保守的布局约束，要求目标 XY 投影包围盒及请求边距落在其中；这不涉及重心稳定。碰撞与接触仍基于实际几何检查。清空体积可以防止三维穿插，但不防止相机前的远处道具遮挡目标：另比较同相机下含环境／不含环境的目标可见性，记录规定阈值下的新增遮挡。轮廓邻近但未遮挡的道具仍可能造成语义混淆，预览中另行审阅。

首版外观对照固定相机与曝光；确需不同相机或物理尺度时，由请求层生成新版本并记录，作者不得静默自动 framing、缩小目标或调整曝光。环境采样可以丰富，不以 `seed` 替代具体参数存档。

### 给 Codex 的最小工具接口（拟议，尚未实现）

| 工具 | 职责与返回 |
|---|---|
| `inspect_request(request_id)` | 读取冻结目标／相机、灰模、占用范围、预留区域、允许资产与预算，不能修改 |
| `check_scene(candidate_id)` | 核验解析规格、实际构建产物、支撑／碰撞、受保护参数、资产及相机空间；返回问题对象、位置及原因 |
| `render_preview(candidate_id)` | 通过前置检查后由固定内核插入 CAD，渲染 RGB、灰模／mask、遮挡诊断和必要全景；返回图像与结构化报告，计入预览预算 |
| `submit_candidate(candidate_id)` | 提交不可变候选版本；控制器按相同哈希重新确认必要检查，记录技术状态与视觉审查状态，不由模型宣称成功 |

工具名称和签名只是合同草案。`candidate_id` 绑定源代码、已解析规格与依赖摘要，代码改动即成为新候选；不能用旧版本的通过报告验收新版本。最终验收强制经过控制器，即使 GPT 没主动调用检查也不能绕过。预览分辨率的通过不能代替最终生产尺寸的可见性／成像检查。

## Metrics

- 技术检查分别报告支撑区域真实性、最小平面距离、最大穿透、支撑覆盖、目标／环境碰撞、额外遮挡、相机和目标合同一致性。容差进入请求与报告，不在验收后调节。
- “拍得到”分三层：入画／深度／裁切在调用前检查；背景新增遮挡比较目标单独可见 mask 与完整场景中目标可见 mask，孔洞和自身遮挡沿参考定义保留；过曝、欠曝、反射与孔槽可辨性另做成像诊断和视觉审阅。mask 检查只是场景合同审计，不是独立的真实感或完整结构证明。
- 人工预览分开记录场景外观、零件外观及结构可读性；未经审阅为 `unreviewed`。技术通过不是“真实感合格”。
- 每个预定请求保留首次结果、尝试次数、错误原因和耗时；后续再做场景多样性与下游评估，不以当前单场景调试宣称覆盖率。

## Decision Rule

接触、无穿插、几何／相机一致和已配置可见性要求属于硬约束。力学稳定性不作为通过条件。视觉是否足够真实是独立的开发判断，不能由 JSON 自报或代码退出码决定。预算耗尽保留候选与失败，不无限重试。

## Edge Cases

- 空／非法目标、非有限坐标、重复对象 ID、无法解析相机或单位：请求错误，不生成默认替代物。
- 多实体选择不明、FOV 方向／图像尺寸缺失且无版本化默认、欧拉约定不明、提示词与相机硬约束冲突：返回具体输入问题；不交给 GPT 猜测。
- 相机原本看不到完整目标，或相机与必需支撑平面冲突：`camera_preflight_failed`，默认不进入场景制作。绝对世界坐标与强制零高度支撑冲突：`placement_camera_conflict`。
- 场景声明平面但实际几何有洞、缺面、起伏或顶面高度不符：`support_geometry_mismatch`。首版支撑区禁用改变实际高度的 displacement；强 bump 造成视觉接触矛盾另行审阅。
- 放置区太小、目标碰到桌沿／道具：`support_region_too_small` 或 `scene_collision`；允许修改场景，不能擅自缩放或旋转 CAD。
- 固定相机被墙或道具遮挡：修改场景或显式失败，不能暗中移动相机。部分原始 CAD 自遮挡不是背景新增遮挡。
- 尖点／边支撑、重心偏移：保留，稳定性仍为 `not_evaluated`；未来物理过滤单独版本化。
- 资产缺失、脚本失败、超时、预算用尽：记录具体状态及已发生成本；不自动下载未知资产或切付费服务。
- 预定请求数大于零但全部失败时成功率为 0；分母为零时为 null，保存分子分母。

## Validation / Sanity Checks

后续实现首先核对 STEP 三角化／导入的坐标、法线与面对应；验证相机输入约定、内外参及共同平移前后的投影一致。再核对相同目标／相机能在桌面与地面两种环境中共享支撑接口；推荐内部坐标下两者顶面均为 `z=0`，桌腿与周围地面只改变环境。最后检查尖点支撑、孔洞支撑、狭小桌面、相机在平面下方、背景遮挡和目标哈希不变等反例。当前仅做文档与 JSON 一致性验证，未执行这些渲染验证。

## Implementation Constraints

先用单进程外层脚本顺序完成“请求→作者→构建／预览→报告→有限修复→保存”。不以实现数据库、并发调度或完整自动场景分类为启动前提。继续使用整体方案的作者适配器与几何保护职责，正式规模化时再接八卡队列。

本轮交付是此协议草案及主方案同步。下一实现交付应为可检查的请求样例、一个场景构建器、场景元数据、固定装配／检查脚本及真实预览；不会把本轮文字协议称为已实现 workflow。
