# Codex 场景程序生成与 CAD 配对渲染工程

当前最小入口：[布景模板生成协议 v0](TEMPLATE_CONTRACT_V0.md)，代码边界见 [代码组织方案](CODE_LAYOUT.md)。模型接收零件集合的 BoundingBox 包络、拍摄预设及分项自然语言，交付可复用环境模板与程序材质。具体 STEP 在后续固定程序批量拍摄时装入。用户确认相机为 `(2,2,2)→原点`、FOV `45°`、`512×512`。以下上层预算／复现设计沿用，单件制作描述以新协议为准。

## Task

设计一套由 Codex／GPT-6 Astra 制作可复用场景程序、由 Blender/Cycles 批量渲染已知 CAD 的数据生产工程。模型参与场景、材质和布局的生成及有限修复；最终像素来自物理渲染。调用单元是场景程序包，渲染单元是 CAD／相机／外观组合。

研究目标：在几何对应可靠的条件下，以可测成本扩展物体材质、拍摄环境及有效场景覆盖，并检验真实照片上的 B-Rep 重建收益。既有三个场景只是启动样例，不限制场景库规模或结构。现有代码与消费接口均不是设计约束。

状态：2026-10-12 设计提案，未实现编排器、未调用新的场景制作模型任务、未生成图片。当前仅核对接口、整理工程合同与研究协议。下述默认预算是可讨论配置，不是已授权长期任务或实测结果。PBR 内容制作要求见 [PBR 基线方案](../PLAN.md)。

当前摸索优先使用 [场景协议 v0 草案](SCENE_CONTRACT_V0.md)：单请求、单场景候选、固定预览及有限修复即可。下文是可扩展工程设计，不要求先实现 campaign 调度、SQLite 或八卡队列。用户已确定首版目标材质不用图片贴图，目标材质由固定程序按数值／函数配方构造。

最新输入约定：STEP 与相机在调用模型前转为受检查的网格、规范相机、灰模和空间约束；不完整提示词只允许补全场景创作字段。已有相机的投影通过明确的共同坐标变换保持，不能只把 CAD 移到地面。拟议的检查／预览工具及相机合同以局部协议为准。

## Assumptions

- **用户资源**：单机 8×RTX 4090，没有支持大量付费 LLM 调用的预算。Codex 推理是远程服务，本机 GPU 用于 Blender 等本地任务；不声称 Astra 在这些 GPU 上运行。
- **已检查的本机事实**：`codex-cli 0.160.1` 可执行，`exec --help` 包含 `--json`、`--output-schema`、`--image`、`--model`、`--output-last-message`、`--cd` 等接口。当前 shell 的 Python 未安装 `openai-codex`；本轮没有安装。接口存在不等于本账号已经验证全部模型和认证路径。
- **官方接口事实**：非交互 CLI、官方 Python／TypeScript SDK 都可用于程序控制。首版选择 Python 调度器封装 `codex exec`，便于记录独立任务产物；适配器边界允许以后改用 SDK。不是对桌面聊天窗口做自动点击。
- **模型**：请求目标为用户指定的 `gpt-6-astra`，记录实际返回标识及推理设置。不静默换模型；别名不等于长期固定 checkpoint，不能保证将来重跑产生同一程序。
- **认证与预算**：优先评估本机已有、受账号额度约束的 Codex 登录方式；不承诺订阅无限调用或免费自动化。API 计费模式默认禁用，不在额度耗尽后自动切换付费后端。认证仅由正式客户端处理，不把 token／auth 文件放入任务或发布包。
- **输入几何**：有源 CAD／可靠网格。只有一张灰模图片不能支持相同的三维保证。CAD 缺物理单位时，尺寸必须作为场景假设记录。
- **Needs confirmation**：可用于外观开发的真实照片来源、目标实拍的场景分布、账号实际可用模型／限额、正式制作总预算。可以先定义合同，不以未知值冒充生产配置。
- **研究边界**：既定 CAD 拓扑、表面和对应关系不可由场景作者修改；照片里的结构可读性仍需独立检查。
- **当前摆放需求（2026-10-12 用户补充）**：单 CAD 保持给定旋转，沿平面法向平移到接触，允许尖点支撑与重心偏移；不执行力学稳定过滤。只检查接触与无穿插，稳定性状态为 `not_evaluated`。详细需求及材质探索分层见 [PBR 方案](../PLAN.md#0-当前需求拆分2026-10-12-用户补充)。
- **当前材质需求**：目标零件采用刚制作完成的外观，只使用数值／程序函数驱动 PBR；目标图片贴图及生成式材质暂缓。场景的桌面／地面等表面仍可使用允许的贴图资产。

## Outputs

每个**场景程序包**需交付：

- `scene_builder.py`：只构建环境的参数化程序，不能读写目标 CAD、渲染器或验收器。
- `parameters.schema.json` 与 `sampling.json`：可变参数、范围、相关采样和不可用组合；不是只暴露一个随机 seed。
- `material_recipes.json`：声明式目标材质配方，使用受审节点与范围；背景材质同样记录依赖与坐标。
- `support.json`：支撑面、目标预留体积、适用尺寸／形状范围和相机可用区域。
- `assets.lock.json`：真实文件哈希、许可与来源；缺资产需要显式报告。
- `preview_manifest.json`、预览图与 `validation.json`：每次制作版本的固定开发面板和失败原因。
- `package.json`：内容哈希、父版本／程序家族、构建器版本、状态、依赖与适用范围。

每次**作者调用**保存任务正文、提示模板及版本、被附加图像与检查报告的哈希、模型请求／实际标识、CLI 版本、相关配置和有效指令、事件 JSONL、最终结构化结果、代码 diff、耗时及可获得的 token 用量。保存可观测调用轨迹，不把无法访问的模型内部推理列为复现要求。

每个**渲染实例**保存 package／asset／CAD 哈希、完整采样参数、CAD→世界→相机变换、内参、尺寸假设、随机数流、渲染与颜色管理版本、RGB、几何参考、状态和耗时。RGB／mask／审计 passes 的格式沿用 PBR 方案的明确约定，不沿用旧 NPZ 对 view 维度的隐式含义。

每个**研究版本**发布冻结场景程序库、可分发资产或可核对的获取清单、制作轨迹摘要、采样列表、环境锁定、失败统计和下游协议。`.blend` 是可检查的辅助产物，不能替代构建源代码、依赖与参数。

## Processing Protocol

### 1. 覆盖规划与任务队列

先制定场景分类和允许组合，由确定性的规划器生成场景任务。Codex 可参与提出新场景类别，但提案必须进入版本化分类与预算后才能执行；不建立无限自主创作循环。

类别可扩展到检测、装配、机加工、维修、实验、包装、仓储、家庭工作区、现场检修等与零件照片相关的用途。空间结构、物体支撑、背景布局和照明需要变化；只换文案、材质颜色或相同房间的 seed 不计为独立场景覆盖。已有三个样例用于启动制作，不是模板上限。初始均衡设计与实拍目标分布估计分别命名。

每个请求有不可变 `job_id`。场景程序修改沿 parent/package family 追踪，防止将克隆程序当作全新环境。规划器可根据开发集的覆盖缺口、近重复和失败分布提出下一批任务，始终受 campaign 预算限制。

### 2. Codex 作者适配器

Python 调度器为每个 job 创建独立制作目录，放入精简任务规格、版本化制作指南、允许使用的资产清单、程序接口和参考。作者不依赖本聊天的隐藏上下文，也不默认继承整份研究仓库及机器上的个人配置。解析后的实际指令与相关配置必须留档。

首版调用边界示意（仅接口示意，本轮未执行）：

```python
argv = [
    "codex", "exec",
    "--cd", str(job_workspace),
    "--model", "gpt-6-astra",
    "--sandbox", "workspace-write",
    "--json",
    "--output-schema", str(author_result_schema),
    "--output-last-message", str(author_result_path),
    "-",
]
# subprocess 以 argv 列表和 stdin 文本调用；保存 stdout JSONL 与 stderr。
# 修复轮附上实际预览图、固定检查报告和当前程序，而非只说“再真实一点”。
```

结果 schema 至少包含 `job_id`、`candidate_package_path`、`candidate_status`、`asset_requests`、`known_limitations`。`candidate_status` 只能陈述候选交付状态；是否通过、是否冻结由独立控制器决定。退出码 0、schema 合法、作者声称完成均不足以入库。

新场景使用独立任务上下文；同一 job 的修复可按明确 session ID 继续，也可用冻结中间产物启动新任务，两种模式需固定并记录。并行时禁止用 `resume --last` 猜测任务。若采用 SDK，保持同一适配器合同，不同时维护互相漂移的两套编排逻辑。

作者只负责程序与修复请求。预览由受控工具／外层调度器提交 GPU 队列，作者不能在内部无限启动 Blender 或绕过预览预算。

### 3. 构建、检查与 CAD 保护边界

隔离编译阶段执行 `scene_builder.py`，生成背景网格、受审材质描述、光源与支撑信息；此阶段没有目标 CAD 写权限。空间规格通过目标预留体积、形状范围和代理物体表达。资产来源事先注册，不让每个场景任务自行全网下载。

可信渲染进程在新场景中加载经过检查的环境数据，再插入源 CAD。第一版生产接口只接收受限场景 JSON、静态三角网格和纹理文件，由可信 loader 创建对象、灯光和材质；作者 `.blend` 仅作审阅产物，不直接加载进入生产。不导入 handlers、drivers、自定义回调或随渲染执行的未知代码。环境 modifiers 若需要，先求值为受检查的静态网格；对数量、大小、纹理分辨率和资产路径设明确资源范围。目标材质先用版本化的受审配方和参数构建；新配方经过同一验证后扩充注册表，不能把任意生成节点组直接带入。

制作／编译进程通过独立运行环境只访问任务目录与只读资产，不能访问生产内核、源 CAD 或账户凭证；编译阶段不需要网络或 GPU。模型客户端认证与生成代码的执行环境分离。只清空 GPU 环境变量或设置工作目录不构成这些边界，实施时必须验证真实访问范围。

可信内核独占：CAD 加载与面对应、相机和允许的刚体变换、输出标签、图像尺寸、渲染设置、检查器、文件状态。目标不允许拓扑修改、Boolean、displacement、透明切除、增添子零件或假倒角。作者不得修改质量阈值或验收样本来提高通过率。

校验源文件哈希以及最终求值网格、面对应、法线处理规则、对象变换和可见性设置。源文件未改不等于实际参与渲染的对象未改。法线、材质和环境仍可能造成视觉误导，因此几何约束不能替代 RGB 审查。

### 4. 固定预览与有限修复

先运行语法、资产、坐标、碰撞、平面接触、相机、材质节点等技术检查，失败则返回明确报告。当前不检查力学稳定性，也不为通过支撑检查擅自旋转 CAD。通过后在开发面板生成场景全景、同视角灰模／RGB、结构细节与不同 seed 的拼图。每轮用同一面板，避免只选当前最好看的一个 CAD。

Codex 读取报告与预览，修改场景／材质代码；首版建议 1 次初稿加最多 2 次修复。几何问题、光照问题、物体材质问题、背景重复分别记录。固定预算结束即保留当前结果和失败状态，不无限抽取新构图。

同一模型的自评可作为修改建议，不是论文的独立真实感真值。人工用开发子集校准判据，候选随后在作者不可见的冻结验收面板上检查；分别报告开发面板与未见 CAD／参数组合的通过率。验收面板不作为下一轮作者修复输入；若将其失败细节用于开发，必须标记该面板已转为开发数据，并为后续验收建立新冻结版本。没有经过视觉判断的候选标为 `unreviewed`。作者不得查看最终实拍测试集。

### 5. 冻结程序库与批量采样

通过独立合同及既定场景发布判据后，以内容哈希冻结 package。保存构建源、参数分布、资产与环境锁定；任何修复产生新版本，禁止原地覆盖已经生成数据所用的程序。

批量规划器按 CAD／去重组 split 选择场景包，进行有约束的参数采样；物体尺寸、材质、视角与场景不要形成无意的固定绑定。相机和结构先验一致后输出完整请求 manifest。生产阶段不逐图调用 Codex，也不因某张图视觉拒收自动开启无限修图。

参数化场景程序先被编译为具体环境实例，同一个实例可复用于多个 CAD；实例在独立进程中按新的采样参数生成，不要求每个参数组合事先人工保存 `.blend`。目标由可信内核最后加入。

同一单机渲染队列管理全部 8 张 GPU：worker 绑定单卡，预览也需取得 GPU 租约；CPU 预处理与写盘并发受限。制作阶段可只开少量预览，生产阶段再使用八卡；不把训练与渲染同时承诺占满整机。

### 6. 状态、恢复与预算

采用 Python 编排、SQLite 事务状态和追加式事件记录即可，不先引入云服务或复杂集群系统。租约、心跳、原子提交与幂等键用于本地去重与恢复；不能保证外部模型调用恰好执行一次或绝不重复计费。调用已发出但结果未落盘时进入 `outcome_unknown`，先核对活动进程、session 和事件日志，不自动重发；确需重发则新建 attempt，全部已发生调用计入成本。Codex 任务和渲染请求分表管理。

场景状态：`planned → authoring → validating → previewing → repairing / ready_to_freeze → frozen`。
图片状态：`requested → rendering → technical_ok → visual_accepted / visual_rejected / unreviewed → archived`。
横向状态：`failed`、`waiting_quota`、`waiting_asset`、`budget_exhausted`、`cancelled`、`outcome_unknown`，分别保留原因与最后有效产物。这些是本地工程状态，不是对本对话 goal 状态的操作。

认证失败／额度耗尽暂停新作者任务；已有冻结场景可继续渲染。普通限速按服务返回信息有限退避，额度耗尽不不断重试，也不通过切账号或付费后端规避。恢复依据 job/package/attempt ID 和落盘产物，不依赖聊天记忆。

预算分开限制：作者并发（建议先 1）、每包外层调用次数、调用墙钟、预览 GPU 秒、场景候选总数、生产请求总数、人工审查分钟。token 字段仅在接口报告后计入；CLI 一次任务内部可有多次模型请求，终止时才提供的 usage 不构成严格实时 token／金额封顶。强制墙钟取消也不能被描述为已精确结算远端费用。

### 7. 三种复现要求

1. **制作过程可审计**：公开任务、提示、工具与图像输入、修改轨迹、调用设置、失败及人工干预。相同提示重跑得到相同程序不作为保证。
2. **冻结产物可重建**：使用发布程序、锁定资产、参数、seed 与环境重建场景，不需重新调用模型。这是数据复现的主要承诺。
3. **渲染可核对**：几何／相机合同必须一致；同环境检查图像容差，跨 GPU／驱动／Blender 不承诺 PNG 逐位一致。公开图像摘要、参考样例及误差口径。

| 层级 | 指标与分母 |
|---|---|
| 场景制作 | 初稿可执行率、预算内程序合格率、每个合格包的调用／token／GPU 秒／人工分钟；分母为全部预定 scene jobs |
| 几何合同 | 源 CAD 与求值网格／面对应／变换一致性，遮挡和接触异常；技术失败、缺失、超时不从分母剔除 |
| RGB 结构 | 轮廓、孔槽、薄壁、柱体的误导与不可辨比例；人工确认与自动信号分列 |
| 真实感 | 物体、背景及接触／反射一致性分别盲评；使用实拍开发参照，模型自评不等于独立真值 |
| 场景覆盖 | 程序家族数、布局／光照／材质覆盖、排除前景后的近重复率、有效簇数；固定特征与聚类阈值并人工核验 |
| 图片生产 | 首次技术成功率、固定预算下联合可用率、未审查比例、每千图 GPU 小时、全部成本／合格图 |
| 下游 | 固定 CAD 数量、图片数与训练曝光后，在独立实拍上评价有效 B-Rep／solid、可见一致性及有 GT 子集的几何误差 |

分别报告“场景程序多样性”与“最终图片多样性”，不能用 prompt 或 seed 数代替。扩大场景库时看成本—覆盖—下游性能曲线，数据数量本身不证明收益。

费用拆成场景库制作、每次渲染和审查三部分。订阅额度消耗、API 实际账单和本地 GPU 时间分开；不把模型调用成本隐藏成免费的预处理。所有失败、修复、丢弃候选都计入制作成本。

## Decision Rule

- 场景必须通过固定技术合同；作者文本和合法 JSON 不具有验收权限。
- 几何／相机错误阻止对应版本入库。视觉阈值在开发集校准并冻结；不直接沿用历史 SAM／CLIP 或旧文档的任意阈值。
- 在预算内无法制作的场景保留为失败／不支持，不能静默改任务定义。缺资产与几何不适用分别记录。
- 扩库依据有效覆盖、背景近重复、首轮可用率和下游证据，不能把数百个外观相似的程序当成数百个独立环境。
- 工程 baseline 可采用“规范场景任务＋Codex 制作＋有限修复＋可信渲染”。是否新增算法由明确失败机制决定，不为了论文形式强行叠加 diffusion。
- 必要消融：有限人工场景库；Codex 场景初稿；加固定预算视觉修复；加覆盖驱动任务选择。所有变体保留相同几何合同，比较固定数据量与固定制作预算两种口径，不能同时改数据量、资产库和检查规则后归因于模型。
- CAD 去重组与场景程序家族分别组织拆分；制作仅看开发面板。隐藏的程序克隆不得跨“未见场景”测试，最终实拍测试不能反馈到作者。

## Edge Cases

- 空分类、重复 job／sample ID、无法解析的资产 ID：分发前报错，不创建虚假完成记录。
- 非法 schema、NaN／Inf、缺脚本、路径逃逸、损坏资产、未声明依赖：技术拒收并记录阶段。
- 材质／场景靠覆盖目标、透明切除、背景物体伪装零件来满足外观：几何与视觉异常分别拒收，不能只检查源 CAD 哈希。
- 长条／薄片与有限台面不兼容或穿插：报告接触问题和该类失败率，不静默缩放或删除。尖点支撑或重心偏移符合当前增强需求，不作为验收失败；力学过滤另行版本化。
- 同 seed 出现变化：核对所有随机源、版本及资产；不把只记录 NumPy seed 称为完整复现。
- 作者改动检查器／可信加载器：拒收并保持核心哈希不变；作者工作目录不包含可写的生产内核。
- 中断时只完成部分文件：写入 staging 后原子提交；恢复不将半成品视为 frozen。
- token 用量或实际模型字段不可得：记录 null 和原因，不填 0 或用请求值冒充实际值。
- 账号限额、服务变更或目标模型不可用：进入明确等待／失败状态，不静默替换模型或开启付费。
- 预定分母大于零而全部失败时成功率为 0；只有分母为零的比例才为 null。合格图数为零时单位合格成本为 null 并报告总成本；无人审查时人工通过率为 null，不影响可计算的技术成功率。保留各自分子分母。

## Validation / Sanity Checks

实施顺序应验证完整工程闭环，而非先大规模制作场景：

1. 固定接口和测试夹具：人工极简场景可通过，故意缺资产、改目标几何、错相机、制造遮挡和重复输出会失败。
2. 在不调用模型的条件下验证编排状态机：进程中断、重复事件、限额、超时、恢复和 GPU 租约；使用回放事件验证，不能伪称已连接服务。
3. 做一个真实 Codex 制作任务，完成输入规格、编译、固定预览、有限修复和冻结；记录全部成本，不只保存最终成功包。
4. 从冻结包在没有 Codex 的环境中重新构建并渲染；核对几何、参数和图像容差。
5. 扩展到多个空间结构与零件形状，验证程序适用范围及场景近重复，再讨论场景库规模和正式数据生产。

不同 scene job 各自持有规格、上下文和状态；并发不得改变相同请求的 seed 派生。GPU 调度和文件写入用故障注入验证。渲染成功与小规模验证均不构成真实照片重建提升的证据。

## Implementation Constraints

以下是较早的规模化职责地图。首版采用 [代码组织方案](CODE_LAYOUT.md) 中独立子项目和十个职责模块，不将这里每个职责都创建为服务、插件或独立层；数据库／并发调度待顺序流程稳定后再实现。

| 模块 | 职责 |
|---|---|
| `contracts` | campaign、job、package、渲染实例及结果 schema |
| `scenario_planner` | 分类、覆盖配额、合法组合、下一批请求 |
| `codex_author` | CLI／SDK 适配、上下文组装、图像反馈、事件与用量记录 |
| `scene_compiler` | 隔离执行背景程序、求值与导出可受控加载的环境数据 |
| `scene_validator` | 资产、布局、支撑、材质、几何合同与固定预览 |
| `scene_registry` | 内容哈希、父版本、家族、冻结与兼容性索引 |
| `render_scheduler` | SQLite 任务、CPU 准备、单卡租约、重试与恢复 |
| `trusted_renderer` | 注入 CAD、相机／材质、标签、固定渲染与元数据 |
| `quality_audit` | 调用统一质量评价，批次抽样、覆盖与报告；避免复制旧指标缺陷 |

普通工作目录隔离不等于生产边界。制作／编译进程与可信渲染进程分离，源 CAD、检查器及环境锁定只读；不把任意生成代码留在最终渲染回调中。无需新增付费服务或逐图 agent。

资产按注册表获取和缓存，生产不临时联网下载。已有代码、模型与数据保留；不修改训练接口、环境或用户其他分支工作。运行产物在被忽略的目录，研究合同和紧凑报告受 Git 管理。

## Deliverables

当前交付：这份工程设计及 PBR 方案中的上层定位更新。后续实现目标是可由命令驱动的场景制作／冻结／渲染／审计流程，不要求用户继续同一聊天。

论文可将方法描述为“由通用多模态编码 agent 生成和修正参数化场景程序，在已知 CAD 几何约束下物理渲染配对图像”。明确 GPT-6 Astra 的实际角色、制作预算、人工参与和数据来源。模型品牌或调用 Blender 本身不是已证实的新贡献；重点验证几何合同、覆盖扩展、成本与实拍下游价值。
